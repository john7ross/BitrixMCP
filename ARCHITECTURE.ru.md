# Архитектура

[English](ARCHITECTURE.md) · **Русский**

`bitrix_mcp` — это stateless-шлюз, отдающий REST API Bitrix24 в виде
MCP-инструментов. У него одна задача: превращать вызовы MCP-инструментов в
авторизованные REST-вызовы Битрикса и честно возвращать результат. Своей БД и
своего состояния сессии у него нет — каждый вызов резолвит вебхук, делает
HTTP-запрос и форматирует ответ.

## Технологии

| Аспект | Выбор | Почему |
|---|---|---|
| Язык | Python ≥ 3.10 | Компактная обёртка REST; широкая переносимость |
| MCP-фреймворк | `mcp[cli]` (официальный SDK, FastMCP) | Декораторы-инструменты, генерация схем, оба транспорта |
| HTTP | `httpx` (async) | Асинхронный клиент, таймауты, редиректы |
| Валидация | Pydantic v2 (через FastMCP) | Ограничения полей + авто JSON-схема |
| Упаковка | Hatchling + uv | Консольная точка входа `bitrix-mcp`; устанавливаемые wheel/sdist |
| Диаграммы | PlantUML (stdlib C4) | Рендерится офлайн |

## Компоненты

См. [docs/diagrams/bitrix_mcp_component.png](docs/diagrams/bitrix_mcp_component.png)
(исходник: [component.puml](docs/diagrams/component.puml)).

- **Точка входа** (`__main__.py`) — разбирает `--transport/--http/--host/--port`
  (и env `BITRIX_*`), затем запускает FastMCP по **stdio** или **Streamable
  HTTP** (stateless JSON). Это два поставляемых фронта одного сервера.
- **Сервер + реестр** (`server.py`) — экземпляр `FastMCP("bitrix24_mcp")` с
  инструкциями сервера; импортирует 16 модулей инструментов через `importlib`,
  чтобы их декораторы `@mcp.tool` зарегистрировали все 87 инструментов.
- **Модули инструментов** (`tools/*.py`) — по модулю на домен (universal, crm,
  tasks, scrum, calendar, disk, users, groups, messaging, lists, catalog, sale,
  documents, bizproc, telephony). Каждый инструмент — тонкая типизированная
  функция, которая собирает `(method, params)` и делегирует в runtime.
- **Runtime** (`runtime.py`) — общий хребет: резолв вебхука, read-only-гейт,
  форматирование JSON, переиспользуемые `Annotated`-типы параметров и хелперы
  `run_call` / `run_list`, которые использует каждый инструмент.
- **Клиент Битрикса** (`client.py`) — единственный код, который ходит по HTTP:
  POST с JSON-телом, честная пагинация (`start`/`next`/`total`), кодировка
  `php_query` для команд batch, классификатор записи и всплытие ошибок
  (`BitrixError`, никогда не глотается).
- **Config** (`config.py`) — читает из окружения `BITRIX_WEBHOOK_URL`,
  `BITRIX_READ_ONLY`, `BITRIX_TIMEOUT`, `BITRIX_MAX_PAGES`.

## Логический вид — путь вызова

См. [docs/diagrams/bitrix_mcp_sequence.png](docs/diagrams/bitrix_mcp_sequence.png)
(исходник: [sequence.puml](docs/diagrams/sequence.puml)).

1. Клиент шлёт `tools/call`; FastMCP валидирует аргументы по сгенерированной
   схеме инструмента и инжектит `Context`.
2. Инструмент вызывает `run_call`/`run_list` с REST-методом и параметрами.
3. Runtime резолвит вебхук (`personal_webhook` > `webhook_url` > заголовок
   `X-B24-Webhook` > `BITRIX_WEBHOOK_URL`) и применяет read-only-гейт.
4. `BitrixClient` шлёт POST с JSON-телом на `…/rest/<id>/<токен>/<method>.json`.
5. При успехе ответ обрезается/пагинируется в конверт; при ошибке Битрикса
   становится структурой `{error, code, message}` — код (напр. `ACCESS_DENIED`)
   сохраняется, не подменяется пустым результатом.

## Модель авторизации

Два уровня вебхука, резолвятся на каждый вызов. Вебхук по умолчанию
(`BITRIX_WEBHOOK_URL`) закрывает типовой случай; `webhook_url` переопределяет его
на один вызов; `personal_webhook` действует от имени конкретного пользователя
(нужен, чтобы писать под его правами). По HTTP заголовок `X-B24-Webhook` может
нести дефолт для конкретного клиента. Опциональный гейт `BITRIX_READ_ONLY=1`
отклоняет write-методы ещё до отправки на портал (классификация по глаголу
метода; типизированные write-инструменты классифицируются всегда верно).

## Виды развёртывания

- **stdio (переносимо):** потребляющий агент запускает `bitrix-mcp` как
  подпроцесс. Ни сетевого сервиса, ни моста — самый надёжный вариант и
  умолчание. Один процесс на агента.
- **Streamable HTTP (общий):** запусти `bitrix-mcp --http` как сетевой сервис;
  много клиентов подключаются к `/mcp`. Stateless-JSON-ответы избегают хрупких
  долгоживущих SSE-сессий, которые мешали прежнему развёртыванию. По умолчанию
  слушает `127.0.0.1`; `--host 0.0.0.0` — чтобы выставить наружу.

Сервер stateless, поэтому горизонтальное масштабирование тривиально (запусти
больше HTTP-инстансов за балансировщиком); единственная зависимость с состоянием
— сам портал.

## Модель покрытия

100% REST API доступно через `b24_call` / `b24_batch`. 87 типизированных
инструментов — эргономичный слой над частыми доменами с учётом нюансов Битрикса
(фильтры JSON-телом, авто `ownerId`, канбан активного спринта, честные ошибки).
Длинный хвост модулей (почта, открытые линии, запись корзины заказов, app
placements) используется через универсальные инструменты.
