# Архитектура

[English](ARCHITECTURE.md) · **Русский**

`bitrix_mcp` — это шлюз, отдающий REST API Bitrix24 в виде
MCP-инструментов. Его основная задача: превращать вызовы MCP-инструментов в
авторизованные REST-вызовы Битрикса и честно возвращать результат: каждый
вызов резолвит вебхук, делает HTTP-запрос и форматирует ответ.

Без настроек он **полностью stateless** — ни БД, ни состояния сессии.
Состояние появляется только вместе с событийным контуром: если включён хотя бы
один из трёх способов получения событий, добавляется один файл SQLite — очередь
событий, архив истории, курсоры поллера и настройки, меняемые агентом.
Подробности — [docs/EVENTS.ru.md](docs/EVENTS.ru.md).

## Технологии

| Аспект | Выбор | Почему |
|---|---|---|
| Язык | Python ≥ 3.10 | Компактная обёртка REST; широкая переносимость |
| MCP-фреймворк | `mcp[cli]` (официальный SDK, FastMCP) | Декораторы-инструменты, генерация схем, оба транспорта |
| HTTP | `httpx` (async) | Асинхронный клиент, таймауты, редиректы |
| Валидация | Pydantic v2 (через FastMCP) | Ограничения полей + авто JSON-схема |
| Упаковка | Hatchling + uv | Консольная точка входа `bitrix-mcp`; устанавливаемые wheel/sdist |
| Диаграммы | PlantUML (stdlib C4) | Рендерится офлайн |

## Компоненты

См. [docs/diagrams/bitrix_mcp_component.png](docs/diagrams/bitrix_mcp_component.png)
(исходник: [component.puml](docs/diagrams/component.puml)).

- **Точка входа** (`__main__.py`) — разбирает `--transport/--http/--host/--port`
  (и env `BITRIX_*`), затем запускает FastMCP по **stdio** или **Streamable
  HTTP** (stateless JSON). Это два поставляемых фронта одного сервера.
- **Сервер + реестр** (`server.py`) — экземпляр `FastMCP("bitrix24_mcp")` с
  инструкциями сервера; импортирует 18 модулей инструментов через `importlib`,
  чтобы их декораторы `@mcp.tool` зарегистрировали все 99 инструментов. Он же
  проставляет низкоуровневому серверу версию пакета — иначе FastMCP оставляет
  там версию самого SDK.
- **Модули инструментов** (`tools/*.py`) — по модулю на домен (universal,
  discovery, crm, tasks, scrum, calendar, disk, users, groups, messaging, lists,
  catalog, sale, documents, bizproc, telephony, events, telegram). Каждый
  инструмент — тонкая типизированная функция, которая собирает
  `(method, params)` и делегирует в runtime.
- **Runtime** (`runtime.py`) — общий хребет: резолв вебхука, read-only-гейт,
  форматирование JSON, переиспользуемые `Annotated`-типы параметров и хелперы
  `run_call` / `run_list`, которые использует каждый инструмент.
- **Клиент Битрикса** (`client.py`) — единственный код, который ходит по HTTP:
  POST с JSON-телом, честная пагинация (`start`/`next`/`total`), кодировка
  `php_query` для команд batch, классификатор записи и всплытие ошибок
  (`BitrixError`, никогда не глотается).
- **Config** (`config.py`) — читает из окружения все настройки `BITRIX_*`:
  вебхук, read-only-гейт, таймаут, лимит страниц, хранилище событий и срок
  хранения, токен и путь приёмника, переключатель pull-канала, TLS-материал и
  настройки Telegram.
- **Слой знаний** (`catalog.py` + `tools/discovery.py`) — офлайн-каталог всех
  документированных методов REST, генерируется `scripts/build_catalog.py`.
  Ранжирует методы для `b24_method_search` по сегментам имени с весом по
  редкости, отдаёт сигнатуры в `b24_method_schema` и сравнивает выданные scope
  со всей поверхностью для `b24_scope_gaps`. Это данные, а не код: не править
  руками, а перегенерировать.
- **Санитайзер секретов** (`sanitize.py`) — единственная точка, через которую
  проходит вывод каждого инструмента, плюс фильтр логирования. Битрикс отдаёт
  URL вебхука в обычных ответах на чтение (генератор документов), а httpx
  логирует его объектом, а не строкой, — поэтому оба пути чистятся централизованно,
  вместо того чтобы каждый инструмент помнил об этом сам.
- **Подсистема событий** (`events/*.py`) — выключена, пока не настроена; см.
  [docs/EVENTS.ru.md](docs/EVENTS.ru.md).
  - `pullchannel.py` — подписка на Push & Pull-канал портала исходящим
    соединением, поэтому работает из-под NAT и VPN.
  - `receiver.py` — эндпоинт исходящего вебхука (`/b24/events`), монтируется
    только на HTTP-транспорте и без `BITRIX_EVENT_TOKEN` отвечает отказом.
  - `phpform.py` — разбирает PHP-формы, которыми Битрикс шлёт данные на эндпоинт.
  - `feeds.py` — поллер за `b24_changes_since`: только исходящие запросы,
    курсоры по лентам, работает там, где два других пути невозможны.
  - `store.py` — очередь SQLite, архив истории, курсоры и состояние ack.
  - `telegram.py` — DSL фильтра и доставка для пересылки пойманных событий.

## Логический вид — путь вызова

См. [docs/diagrams/bitrix_mcp_sequence.png](docs/diagrams/bitrix_mcp_sequence.png)
(исходник: [sequence.puml](docs/diagrams/sequence.puml)).

1. Клиент шлёт `tools/call`; FastMCP валидирует аргументы по сгенерированной
   схеме инструмента и инжектит `Context`.
2. Инструмент вызывает `run_call`/`run_list` с REST-методом и параметрами.
3. Runtime резолвит вебхук (`personal_webhook` > `webhook_url` > заголовок
   `X-B24-Webhook` > `BITRIX_WEBHOOK_URL`) и применяет read-only-гейт.
4. `BitrixClient` шлёт POST с JSON-телом на `…/rest/<id>/<токен>/<method>.json`.
5. При успехе ответ обрезается/пагинируется в конверт; при ошибке Битрикса
   становится структурой `{error, code, message}` — код (напр. `ACCESS_DENIED`)
   сохраняется, не подменяется пустым результатом.

## Модель авторизации

Два уровня вебхука, резолвятся на каждый вызов. Вебхук по умолчанию
(`BITRIX_WEBHOOK_URL`) закрывает типовой случай; `webhook_url` переопределяет его
на один вызов; `personal_webhook` действует от имени конкретного пользователя
(нужен, чтобы писать под его правами). По HTTP заголовок `X-B24-Webhook` может
нести дефолт для конкретного клиента. Опциональный гейт `BITRIX_READ_ONLY=1`
отклоняет write-методы ещё до отправки на портал (классификация по глаголу
метода; типизированные write-инструменты классифицируются всегда верно).

## Виды развёртывания

- **stdio (переносимо):** потребляющий агент запускает `bitrix-mcp` как
  подпроцесс. Ни сетевого сервиса, ни моста — самый надёжный вариант и
  умолчание. Один процесс на агента.
- **Streamable HTTP (общий):** запусти `bitrix-mcp --http` как сетевой сервис;
  много клиентов подключаются к `/mcp`. Stateless-JSON-ответы избегают хрупких
  долгоживущих SSE-сессий, которые мешали прежнему развёртыванию. По умолчанию
  слушает `127.0.0.1`; `--host 0.0.0.0` — чтобы выставить наружу.

Сервер без событийного контура stateless, поэтому горизонтальное масштабирование
тривиально (запусти больше HTTP-инстансов за балансировщиком); единственная
зависимость с состоянием — сам портал.

С включённым событийным контуром это уже не так: файл SQLite рассчитан на
один процесс. Несколько инстансов за балансировщиком либо получат каждый
свою базу (и свою часть событий), либо будут конкурировать за один файл.
Правильная схема — один экземпляр с событиями, остальные без них.

## Модель покрытия

100% REST API доступно через `b24_call` / `b24_batch`, а найти нужный метод и
его сигнатуру помогает каталог из официальной документации (`b24_method_search`,
`b24_method_schema`, `b24_scope_gaps` — см. [REQUIREMENTS.ru.md](REQUIREMENTS.ru.md),
требование Т-1). 99 типизированных
инструментов — эргономичный слой над частыми доменами с учётом нюансов Битрикса
(фильтры JSON-телом, авто `ownerId`, канбан активного спринта, честные ошибки).
Длинный хвост модулей (почта, открытые линии, запись корзины заказов, app
placements) используется через универсальные инструменты.
