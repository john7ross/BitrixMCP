# Требования

[English](REQUIREMENTS.md) · **Русский**

Твёрдые требования к проекту. В отличие от `ROADMAP.md`, это не список планов —
это то, чему реализация обязана соответствовать. Изменение любого пункта здесь
требует явного решения, а не молчаливого дрейфа.

## Т-1. 100% охват REST API Bitrix24

**Статус: обязательное. Владелец: Sergey Lebedev.**

Любой метод REST API Bitrix24 должен быть вызываем через этот сервер. Ни один
метод не может быть недостижим из-за того, что для него «не написали
инструмент».

### Что считается выполнением

Требование выполнено, когда для произвольного документированного метода агент
может: (1) узнать, что метод существует, (2) узнать его точные параметры,
(3) вызвать его. Все три шага — без выхода за пределы этого сервера и без
догадок о сигнатуре.

### Как достигается

Через **два уровня**, а не через 1:1-обёртки:

1. **Исполнение** — `b24_call` и `b24_batch` уже дают доступ к любому методу.
   Это ядро требования, и оно закрыто.
2. **Знание** — каталог методов, собранный из официальной документации
   (`github.com/bitrix24/b24restdocs`, источник apidocs.bitrix24.ru): имя
   метода, скоуп, параметры с типами и обязательностью, признак deprecated.
   Инструменты поиска метода и получения его схемы.
3. **Диагностика** — сверка выданных вебхуку скоупов с каталогом, чтобы
   `ACCESS_DENIED` и `ERROR_METHOD_NOT_FOUND` превращались в конкретный список
   «какие права добрать», а не в тупик.

### Почему не по одному инструменту на метод

В официальной документации **1930 методов**. Столько описаний инструментов не
поместится ни в один контекст, и выбор нужного превратится в лотерею.
Типизированные инструменты остаются тем, чем они и были — эргономикой для
частых сценариев, а не механизмом охвата. Пункт «типизированное покрытие 1:1
вне охвата» в `ROADMAP.md` этому требованию не противоречит: охват
обеспечивается уровнями 1–3, а не количеством обёрток.

### Что ломает требование

- Метод, который нельзя вызвать, потому что сервер о нём не знает и не может
  подсказать его схему.
- Молчаливое сужение: если типизированный инструмент не поддерживает какой-то
  параметр метода, у агента должен оставаться путь через `b24_call`.
- Каталог, отставший от документации. Он пересобирается скриптом из
  первоисточника — обновление обязано быть воспроизводимым, а не ручным.

### Проверка

- Каталог содержит не меньше методов, чем актуальная документация.
- Для каждого метода за типизированным инструментом каталог знает его схему.
- Диагностика скоупов на реальном портале даёт список недостающих прав.

## Т-2. Универсальность развёртывания

**Статус: обязательное.**

Сервер не подстраивается под конкретный портал, конкретного пользователя и
конкретную сеть. Права пользователя, установленные модули, доступность портала
извне — всё это параметры среды, а не константы.

Следствия:

- Инструмент **не удаляется** из-за того, что на портале разработчика не хватает
  прав или модуля. `ACCESS_DENIED` — это диагноз среды, а не дефект кода.
- Обнаружение изменений даёт **три пути**, включаемые через `.env`, потому что
  ни один не работает во всех средах:
  - **pull-канал** (Push&Pull) — исходящее соединение к push-серверу портала,
    тот же механизм, которым живут мобильное и десктопное приложения. Real-time,
    не требует ни входящего URL, ни правил файрвола, ни прав администратора,
    работает из-под NAT и VPN. Лучший дефолт для локального запуска. Адреса и
    каналы берутся из `pull.config.get` — он, в отличие от
    `pull.application.config.get`, доступен обычному вебхуку. Время жизни канала
    12 часов, требуется обновление.
  - **приёмник исходящего вебхука** (push) — для развёртываний, где сервер
    постоянно доступен по HTTP и портал может до него достучаться. Единственный
    путь с документированным каталогом событий.
  - **опрос по дате изменения** (poll) — универсальный fallback, когда
    push-сервер выключен. Не видит удалений и промежуточных состояний.
- Транспорт stdio остаётся без внешнего состояния, когда ничего из событийного
  контура не сконфигурировано.

## Т-3. Честность вывода

**Статус: обязательное.**

- Ошибка Битрикса поднимается со своим кодом и никогда не подменяется пустым
  результатом.
- Секреты не попадают в вывод: URL вебхука и `application_token` вырезаются
  перед тем, как ответ уйдёт модели или ляжет в базу.
- Ограничение, которое нечем закрыть, документируется как ограничение, а не
  выдаётся за исправленное.
