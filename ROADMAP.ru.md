## Статус: функционально готов (v0.1.0)

Набор инструментов для этого релиза закрыт. 99 типизированных инструментов на 17
доменов плюс универсальный хребет `b24_call` / `b24_batch` и каталог методов
из официальной доки (100% охват API — и вызов, и знание сигнатур),
чтение и запись, оба транспорта, три способа получения событий с архивом и
пересылкой в Telegram. Офлайн-верификация зелёная (132 теста); живая проверка на
реальном портале выполнена от начала до конца (см. «История») — чтение по всем
доменам плюс полные циклы записи (задача, рабочая группа, событие календаря,
файл на диске — каждое создано, проверено и удалено, ничего существующего не
затронуто).

## История

- **Пересборка по полевым заметкам.** Заменена багованная внутренняя обёртка.
  Задокументированные проблемы исправлены архитектурно, не заплатками:
  - фильтры уходят JSON-телом (чинит игнор фильтра / выгрузку всего портала);
  - ошибки Битрикса всплывают со своим кодом (больше нет фейкового «0
    результатов»);
  - `ownerId` календаря авторезолвится;
  - канбан Scrum через активный спринт + `tasks.api.scrum.kanban.getStages`;
  - телефония через корректный `voximplant.statistic.get`;
  - stdio / stateless HTTP вместо хрупкого SSE-моста `mcp-remote`.
- **База на чтение → полная запись.** Добавлены CRUD и действия с побочными
  эффектами по CRM, задачам, календарю, диску, мессенджеру, спискам, каталогу,
  группам, бизнес-процессам, с опциональным read-only-гейтом.
- **Ширина для ежедневного использования.** Расширено с 8 до 15
  типизированных доменов (воронки, статусы, активности, реквизиты, товарные
  строки, связи сделка-контакт, стадии/чек-листы/время/результаты задач, рабочие
  группы, заказы, генерация документов, чаты/лента, универсальные списки).
- **Живое тестирование на боевом портале.** Полный проход по чтению плюс циклы
  записи create→verify→delete (задача с комментарием/чек-листом/временем/
  завершением; рабочая группа с обновлением; событие календаря с участниками;
  файл на диске) выявили и исправили три доп. краевых случая сверх исходной
  пересборки — см. таблицу багов в README: у `department.get` вообще нет
  серверного фильтра (ограничение Битрикса, теперь фильтруется на клиенте),
  пустая строка в коде ошибки Битрикса проскакивала мимо проверки на
  истинность, а `calendar.event.add`/`.update` молча теряли `attendees` без
  явного `is_meeting`. Также обнаружено (не баг кода): `b24_disk_file_content`
  требует, чтобы исходящий IP сервера был разрешён в WAF портала — иначе
  *скачивание* файла падает 403, хотя вызовы метаданных проходят нормально;
  нужно попросить админа портала добавить хост сервера в белый список.
- **Перенос/чтение Scrum-доски спринта, найдено вживую вместе с оператором на
  реальной доске.** Перенос карточки через `STAGE_ID` в `tasks.task.update`
  выглядел успешным (200 OK, корректное чтение назад), но карточку тихо не
  переносил — проверено взглядом на саму доску, а не только на ответ API.
  Добавлен `b24_scrum_task_move` (`tasks.api.scrum.kanban.addTask` — метод для
  доски, найденный в официальной REST-документации Битрикса после того, как
  неправильный метод был исключён). Дальнейшее тестирование показало, что и
  **чтение** ненадёжно: как только задачу перенести правильно, `STAGE_ID` в
  `tasks.task.get`/`.list` протухает и больше не обновляется, а публичного
  метода для чтения истинного соответствия задача↔колонка на доске спринта
  нет. **Решается не через REST.** Push&Pull-канал портала транслирует переход
  в момент перемещения: событие `tasks / task_update` несёт `BEFORE.STAGE`,
  `AFTER.STAGE` и `AFTER.STAGE_INFO` с id колонки. Проверено вживую на реальной
  доске — карточка перенесена, событие поймано. Истинное соответствие
  задача↔колонка накапливается из этих переходов; REST по-прежнему его не
  отдаёт, и это ограничение REST, а не проекта. **Частично отменено аудитом
  закрытия ниже:** один `kanban.addTask` НЕ переносит уже разложенную карточку —
  рабочий перенос это `deleteTask`, затем `addTask`.
- **Аудит закрытия релиза (v0.1.0).** Вся поверхность перепроверена на боевом
  портале, домен за доменом, и проход выявил двенадцать дефектов, которые прошлое
  заявление «функционально готов» пропустило. Все устранены:
  - `b24_task_comments_list` возвращал `[]` для задачи, у которой комментарии
    заведомо есть. На этом портале они лежат в **чате** задачи, а не в старом
    forum-топике (`forumTopicId` пуст), инструмент же читал только форум —
    успешная запись выглядела как провалившаяся. Теперь читает форум, при пустом
    результате падает в чат и сообщает, какой источник ответил.
  - `b24_calendar_event_list` отдавал все поля всех событий без способа сузить
    выборку: месяц по одному пользователю — **232 события × 60 полей ≈ 1 МБ**,
    достаточно, чтобы выжечь контекст агента одним вызовом. Добавлены `select` и
    `limit` с компактным набором по умолчанию (те же данные — ~16 КБ), честный
    `total` и флаг `truncated`; `select=['*']` по-прежнему отдаёт всё по запросу.
  - `b24_method_search` считал подстроки, взвешивая все слова одинаково: «on»
    совпадал внутри `sonet_group`, а частые слова забивали редкие. Из 15
    реалистичных запросов по смыслу до нужного метода доходили лишь 4 — «search
    users by name» не возвращал `user.search` вообще. Заменено на сегментное
    совпадение, IDF-веса, карту синонимов под нейминг Битрикса (перенос по доске
    — `kanban.addTask`, рабочая группа — `sonet_group`) и понижение обработчиков
    событий. Теперь 15/15, закреплено тестами.
  - `_extract_list` не распознавал именованный ключ-обёртку со словарём по id,
    из-за чего `crm.documentgenerator.template.list` отдавал **19 шаблонов одной
    искажённой записью**, а `total` показывал 19 — противоречащий сам себе
    результат без единой ошибки.
  - Сервер представлялся клиентам **версией MCP SDK** (1.28.1) вместо своей,
    потому что FastMCP её не пробрасывает. Теперь отдаёт версию пакета, читая её
    из метаданных, а не из второго захардкоженного места.
  - `scripts/events_tools_check.py` печатал `FAIL` и завершался кодом **0** —
    сломанный прогон выглядел зелёным. Теперь делает реальные проверки и
    возвращает честный код, доказано в обе стороны принудительным провалом.
  - `pydantic`, `starlette` и `uvicorn` импортировались напрямую, но нигде не
    объявлялись — доставались по случайности через `mcp[cli]`. Объявлены.
  - Десять из пятнадцати скриптов, включая все проверочные, не были описаны
    нигде. Теперь сведены в таблицу в README на обоих языках.
  - Расхождения в документации: количество тестов значилось как 106, а русские
    документы заявляли 1901 метод каталога против 1930 в английских. Приведено к
    измеренным значениям.
  - **`b24_scrum_task_move` ничего не переносил, а документация утверждала обратное.**
    Замечено оператором: карточка двигалась у него, но не у коллег, при этом
    историю изменений видели все. Перепроверено на живой доске: `kanban.addTask`
    только *кладёт* карточку, которой на доске нет, — для уже разложенной он
    возвращает `true` и не делает ничего, поэтому доска не менялась ни у кого.
    `tasks.task.update` со `STAGE_ID` ещё хуже: пишет поле и видимую всем запись
    в историю, а карточка остаётся на месте — ровно то полу-перенесённое
    состояние, которое и наблюдалось. Работает связка `kanban.deleteTask`, затем
    `kanban.addTask`, подтверждена наблюдением за доской. При этом `STAGE_ID`
    ничего из этого не подтверждает — он показывал `0`, пока карточка стояла в
    целевой колонке. Попутно выяснено: `tasks.api.scrum.task.update` с полем
    `entityId` действительно переносит задачу между бэклогом и спринтом, а поля
    колонки у этой сущности нет вовсе.
  - **Пересылка в Telegram впервые проверена сквозным прогоном** — портал →
    pull-канал → хранилище → фильтр → чат, без всякого публичного URL
    (pull-канал работает только исходящими соединениями). Она работает, и
    попутно вскрыла дефект удобства, который офлайн-тесты фильтра поймать не
    могли: портал шлёт `tasks/user_counter` и `tasks/user_efficiency_counter`
    почти на каждое действие, под `tasks/*` они попадают, и одна задача,
    созданная, переименованная и прокомментированная, дала четыре
    сообщения-счётчика против четырёх полезных. Пресеты `work` и `tasks` теперь
    исключают `*counter*`; `everything` — намеренно нет.
  - **Собранный пакет невозможно было установить.** У `mcp[cli]>=1.2.0` не было
    верхней границы, поэтому чистая установка резолвилась в **mcp 2.0.0**, где
    `mcp.server.fastmcp` заменён на `mcp.server.mcpserver`, — пакет падал на
    `import`, ещё до запуска любого инструмента. Разработка этого не видела,
    потому что `uv.lock` фиксирует 1.28.1; дефект вскрылся только при установке
    колеса в одноразовое окружение. Ограничено до `<2` и перепроверено:
    пересобранное колесо поставлено в чистое окружение и запущено против живого
    портала вне репозитория.

  Не дефекты — зафиксировано, чтобы следующий аудит не поднимал их заново: CRM
  отвечает `ACCESS_DENIED` для пользователя этого вебхука (право портала, при
  этом фикс пустого кода ошибки корректно сохраняет сообщение); `tasks.task.get`
  по удалённой задаче возвращает `[]`, а не ошибку — так ведёт себя сам Битрикс,
  обёртка передаёт честно; телефония отвечает `ERROR_METHOD_NOT_FOUND`, потому
  что scope действительно не выдан, ровно как предсказывает `b24_scope_gaps`.

## Вне охвата (осознанно)

- **Типизированное покрытие всего API 1:1.** В документации 1930 методов — столько
  описаний инструментов не поместится ни в один контекст. Это ограничение на
  *способ*, а не на охват: требование [Т-1](REQUIREMENTS.ru.md) (100% охват API)
  закрывается универсальными инструментами плюс каталогом методов из официальной
  документации, а не количеством обёрток.
- **Инфраструктура приложений** (`event.bind`, placements, OAuth-флоу
  приложений) — это webhook-клиент, а не приложение Bitrix Market. Проверено на
  живом портале: входящему вебхуку `event.get` отвечает `WRONG_AUTH_TYPE`,
  так что это ограничение типа авторизации, а не выбор проекта.
  **Сами события при этом в охвате** — тремя другими путями: pull-канал,
  приёмник исходящего вебхука и поллер, см. [docs/EVENTS.ru.md](docs/EVENTS.ru.md).
- **Знание о каком-либо потребляющем приложении.** Сервер — generic-шлюз;
  маппинг его вывода в контракт downstream-приложения живёт в агенте, не здесь.
- **Запись корзины/заказов магазина** — многошаговая; пока через `b24_call`,
  до появления явной потребности в типизированном флоу.

## Возможное развитие (не в обязательствах)

- **Переход на API MCP SDK 2.x.** Зависимость ограничена `mcp<2`, потому что в
  2.0 `mcp.server.fastmcp` заменён на `mcp.server.mcpserver`. Оставаться на 1.x
  пока нормально, но эта граница — срок, а не постоянное решение: перейти нужно до
  того, как 1.x перестанет получать исправления.
- Типизированные обёртки для открытых линий и почты, если появится ежедневный
  спрос.
- Курсорный хелпер для очень больших выгрузок сверх лимита страниц.
- Опциональная авторизация по API-ключу перед HTTP-транспортом.
