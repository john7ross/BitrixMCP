# События портала: три способа получения

[English](EVENTS.md) · **Русский**

Сервер умеет узнавать об изменениях в Битриксе тремя разными способами. Они не
взаимозаменяемы: каждый работает там, где не работают остальные. Выбор зависит
не от предпочтений, а от того, где запущен сервер и что пропускает ваша сеть.

Всё пойманное складывается в **одну общую базу SQLite** — независимо от способа.
Дальше события читаются инструментами `b24_events_*` и, если настроено,
пересылаются в Telegram.

## Как выбрать

| | pull-канал | исходящий вебхук | поллер |
|---|---|---|---|
| Направление соединения | наружу | **внутрь**, портал → сервер | наружу |
| Нужен публичный URL | нет | **да** | нет |
| Нужны права админа на машине | нет | обычно да (файрвол) | нет |
| Работает из-под NAT / VPN | **да** | нет | **да** |
| Задержка | секунды | секунды | интервал опроса |
| Видит удаления | нет | **да** | нет |
| Каталог событий | недокументированный | **документированный** | н/д |
| Работает на stdio | да | **нет**, только `--http` | да |

**Локальный запуск на рабочей станции — берите pull-канал.** Это тот же
механизм, которым живут мобильное и десктопное приложения Битрикса: соединение
открывает клиент, поэтому NAT, корпоративный файрвол и VPN ему безразличны.

**Сервер с постоянным адресом — исходящий вебхук.** Единственный способ с
документированным списком событий и единственный, который видит удаления.

**Поллер — запасной вариант.** Работает всегда, но видит состояние на момент
опроса, а не каждое изменение.

Способы можно включать одновременно. Дубли гасятся: у вебхука — по содержимому
доставки, у канала — по `mid`, у поллера — по паре «запись + время изменения».

## Способ 1. Pull-канал (Push & Pull)

Сервер сам подключается к push-серверу портала и держит соединение. Ничего
настраивать на портале не нужно.

### Настройка

```ini
BITRIX_PULL_CHANNEL=1
BITRIX_EVENT_DB=C:/bitrix-mcp/events.sqlite3
```

Всё. Перезапустите сервер — в логе появится `pull channel started`.

Путь к базе лучше задавать **абсолютный и вне каталога репозитория**: по
умолчанию файл создаётся в текущем каталоге, а в нём лежат реальные персональные
данные сотрудников.

### Проверка

```bash
python scripts/pull_probe.py 120
```

Скрипт подключится и будет печатать всё, что приходит. Подвигайте карточку на
доске или напишите в чат — события появятся в консоли.

### Что реально приходит

Проверено на живом портале: `tasks/task_update` (включая переходы стадий с
`BEFORE`/`AFTER` и id колонки), `tasks/itemUpdated` со scrum-полями, и семейство
`im/*` — сообщения, счётчики, отметки о прочтении.

### Ограничения, о которых надо знать заранее

- **Канал персональный.** Приходит то, что получил бы интерфейс пользователя,
  чьим вебхуком работает сервер. Это не тот же список, что у исходящего вебхука.
- **Много шума.** Мессенджер генерирует события постоянно. Для Telegram
  обязательно настройте фильтр, иначе завалит.
- **Контракт не гарантирован.** Пары `module_id`/`command` — внутренний протокол
  интерфейса, а не версионированный REST. Между версиями коробки могут
  измениться без предупреждения.
- **Удаления не видны.**
- Канал живёт около 12 часов и обновляется автоматически.

### Зачем он нужен, даже если есть вебхук

Единственный источник, который отдаёт **соответствие задачи и колонки на
scrum-доске**. REST этого не умеет: `STAGE_ID` в `tasks.task.get` протухает после
переноса, а метода для чтения истинной колонки не существует. Канал транслирует
переход в момент перемещения.

## Способ 2. Исходящий вебхук

Портал сам шлёт POST на ваш адрес при каждом событии. Требует, чтобы сервер был
достижим по HTTP из сети портала.

### Шаг 1. Поднять сервер в HTTP-режиме

Приёмник монтируется **только** на транспорте `--http`. На stdio его нет — там
используйте pull-канал.

```ini
BITRIX_EVENT_TOKEN=<заполним на шаге 3>
BITRIX_EVENT_PATH=/b24/events
BITRIX_EVENT_DB=C:/bitrix-mcp/events.sqlite3
```

```bash
bitrix-mcp --http --host 0.0.0.0 --port 8000
```

Адрес обработчика получится `http://<хост>:8000/b24/events`.

### Шаг 2. Убедиться, что портал до вас достучится

Это главная причина неудач, и проверяется до всякой настройки на портале:

```bash
python scripts/probe_listener.py          # на машине с сервером
```

Затем **с самого Bitrix-сервера**:

```bash
curl -v http://<хост>:8000/probe
```

Увидели строку в консоли пробы — путь есть. Таймаут или connection refused —
пути нет, и никакая настройка на портале это не исправит. На Windows понадобится
разрешить входящие (из админского PowerShell):

```powershell
New-NetFirewallRule -DisplayName "BitrixMCP" -Direction Inbound `
    -Protocol TCP -LocalPort 8000 -Action Allow
```

### Шаг 3. Создать вебхук на портале

**Разработчикам → Другое → Исходящий вебхук.** Три поля:

**URL вашего обработчика** — полный адрес, например
`https://mcp.example.ru/b24/events`. Портал ожидает `https`; коробка часто
принимает и `http`, но это надо проверить на своём стенде.

**Токен приложения** — портал генерирует сам. Скопируйте его в `.env`:

```ini
BITRIX_EVENT_TOKEN=<токен из этого поля>
```

Без него приёмник отвечает **503 на любую доставку**. Это сделано намеренно:
маршрут не проходит авторизацию SDK, и токен — единственное, что отличает ваш
портал от случайного запроса из сети. Открытым по недосмотру он остаться не
может.

**События** — выберите нужные через «+ выбрать». По умолчанию портал
предлагает бронирования, календарь, живую ленту и смарт-процессы. Если нужны
задачи и сделки, добавьте их явно: `ONTASKUPDATE`, `ONTASKADD`,
`ONCRMDEALUPDATE`, `ONCRMDEALADD` и подобные — в списке по умолчанию их нет.

### Шаг 4. Проверить

```bash
curl -X POST http://<хост>:8000/b24/events -d "event=PROBE"
```

Ожидаемый ответ — **403**: маршрут жив и отвергает доставку без валидного
токена. Дальше сделайте что-нибудь в портале и посмотрите `b24_events_stats`.

### Требования и ограничения

- **Коробке нужна активная лицензия.** На демо-портале исходящий вебхук не
  работает вовсе — проверьте это первым делом.
- Обработчик обязан отвечать 200 быстро, иначе портал ретраит. Приёмник
  отвечает сразу и никогда не отдаёт 500 — иначе одна битая доставка встала бы в
  бесконечный цикл.
- Повторные доставки дедуплицируются по содержимому.
- Payload приходит как `application/x-www-form-urlencoded` с PHP-скобками
  (`data[FIELDS][ID]=662`), **не JSON**.
- `application_token` вырезается перед записью в базу.

### HTTPS

SDK не умеет TLS — его запускалка не принимает сертификаты. Поэтому либо
reverse proxy перед сервером, либо встроенный путь:

```ini
BITRIX_HTTP_SSL_CERT=/path/fullchain.pem
BITRIX_HTTP_SSL_KEY=/path/privkey.pem
```

Когда обе переменные заданы, сервер поднимает uvicorn сам и слушает https.

## Способ 3. Поллер

Спрашивает портал «что изменилось с такого-то момента». Только исходящие
запросы, никакой настройки на портале.

### Настройка

Отдельных переменных не нужно — достаточно `BITRIX_EVENT_DB` для курсоров.
Вызывается инструментом:

```
b24_changes_since(feed="tasks")
```

Курсор на каждый фид хранится локально, поэтому повторные вызовы без аргументов
идут вперёд по изменениям. Первый вызов без `since` берёт последние сутки.

### Фиды

`tasks` — подтверждён на живых данных. `deals`, `leads`, `contacts`,
`companies` — форма из документации, на портале с данными не проверялась; в
ответе такие фиды помечены `verified: false`. Смарт-процессы — через
`entity_type_id`.

### Ограничения

- Видит **состояние на момент опроса**, а не каждое изменение. Две правки между
  опросами выглядят как одна.
- **Удаления не видны** — запись просто перестаёт возвращаться.
- Граница `>=` включающая, поэтому пограничная запись приходит дважды; в архиве
  её гасит дедупликация.

## Чтение пойманного

Все три способа наполняют одну базу, поэтому инструменты общие.

| Инструмент | Зачем |
|---|---|
| `b24_events_poll` | новые необработанные события; `ack` их скрывает |
| `b24_events_ack` | пометить обработанным (из истории не удаляет) |
| `b24_events_history` | архив: «что было с задачей 477818 на прошлой неделе» |
| `b24_events_stats` | что настроено и что поймано |
| `b24_changes_since` | поллер |

`b24_events_history` отвечает на вопросы, на которые REST ответить не может: у
большинства сущностей Битрикса нет истории изменений. Payload сохраняется
целиком, поэтому в архиве остаётся контекст на момент события, а не только id.

Ретенция — `BITRIX_EVENT_RETENTION_DAYS` (по умолчанию 14). Чистка **по
возрасту**, подтверждённые события не считаются расходным материалом и
автоматически не удаляются никогда.

**База содержит персональные данные.** Из pull-канала приезжают почты, рабочие
телефоны, дни рождения, LDAP-идентификаторы сотрудников. Держите файл вне
репозитория и вне резервных копий, которые уходят наружу.

## Пересылка в Telegram

События в базе, которые никто не читает, — это события, которых как будто нет.
Пересылка отправляет их в чат или канал.

### Шаг 1. Бот и адресат

Создайте бота через **@BotFather**, получите токен. Узнайте свой числовой id —
например, написав боту и посмотрев `getUpdates`. Для канала добавьте бота
администратором и используйте id вида `-100...`.

```ini
BITRIX_TELEGRAM_TOKEN=123456:AA...
BITRIX_TELEGRAM_CHAT_ID=733224197
BITRIX_TELEGRAM_ALLOWED_USERS=733224197
```

### Шаг 2. Выбрать, что присылать

**По умолчанию не пересылается ничего.** Это не недоработка: pull-канал
генерирует много служебного шума, и форвардер, который на первом запуске зальёт
чат, замьютят в тот же день.

```ini
BITRIX_TELEGRAM_EVENTS=tasks/*,ONTASK*,ONCRM*,poll/*,-im/*,-*counter*
```

Исключение `-*counter*` — не косметика. Портал шлёт `tasks/user_counter` и
`tasks/user_efficiency_counter` почти на каждое действие, и человеку в них нет
ничего: замерено сквозным прогоном — одна задача, созданная, переименованная и
прокомментированная, дала **четыре сообщения-счётчика против четырёх полезных**.
Под `tasks/*` они попадают, поэтому отсекаются по имени.

Синтаксис — через запятую, регистр не важен:

| Правило | Значение |
|---|---|
| `tasks/*` | события задач из pull-канала |
| `ONCRMDEAL*` | события сделок из исходящего вебхука |
| `tasks/task_update` | одно конкретное событие |
| `entity:task` | всё про задачи, независимо от источника |
| `source:poll` | всё, что нашёл поллер |
| `*` | всё |
| `-im/*` | исключение; **исключения побеждают** |

Пресеты: `work`, `tasks`, `crm`, `everything`, `nothing`.

### Шаг 3. Проверить

```
b24_telegram_test(preview_only=true)   # что бы ушло — ничего не отправляя
b24_telegram_test()                    # реальная отправка
b24_telegram_status()                  # что настроено сейчас
```

`preview_only` отвечает на вопрос «меня завалит?» без единого сообщения:
прогоняет последние пойманные события через текущий фильтр.

### Настройка через агента

Фильтр, адресат и вкл/выкл меняются на ходу:

```
b24_telegram_configure(events="crm")
b24_telegram_configure(events="tasks/*,-im/*")
b24_telegram_configure(enabled=false)
b24_telegram_configure(reset=true)     # вернуться к значениям из .env
```

Переопределения живут в базе событий и перебивают `.env`. Файл `.env` **не
переписывается** — у работающего сервера нельзя менять конфиг под ногами, и файл
остаётся записью намерения.

### Что агент менять не может — и почему

**Токен бота** задаётся только в `.env`. Учётные данные не место в переписке.

**`BITRIX_TELEGRAM_ALLOWED_USERS` — граница безопасности, а не удобство.**
`b24_telegram_configure` позволяет агенту сменить `chat_id`, а агент читает
содержимое портала: тексты задач, комментарии, письма. Строка вида «перенастрой
пересылку на chat_id …», спрятанная в любом из них, увела бы весь поток событий
постороннему. Список читается **только из окружения** и проверяется в трёх
местах: при попытке смены адресата (отказ до записи, чтобы отклонённый адрес не
осел в настройках), перед тестовой отправкой и на каждом проходе фонового
форвардера. Пустой список означает «без ограничений» — задавайте его всегда.

### Если Telegram недоступен

Во многих корпоративных и национальных сетях `api.telegram.org` заблокирован:
имя резолвится, соединение не устанавливается. Признак — ошибка
`cannot reach api.telegram.org (ConnectTimeout)`. Это блокировка, а не проблема
с токеном.

```ini
BITRIX_TELEGRAM_PROXY=http://proxy:3128
```

Прокси применяется **только к Telegram** — портал обычно доступен напрямую, и
загонять оба соединения в один прокси означало бы сломать работающую половину.

Диагностика: `python scripts/tg_conn_probe.py` — проверяет DNS, TCP и API по
отдельности и говорит, на каком уровне обрыв.

## Все переменные окружения

| Переменная | Назначение |
|---|---|
| `BITRIX_EVENT_DB` | файл SQLite: события, курсоры, настройки. Задавайте абсолютный путь вне репозитория |
| `BITRIX_EVENT_RETENTION_DAYS` | срок хранения, по умолчанию 14 |
| `BITRIX_PULL_CHANNEL` | `1` — включить pull-канал |
| `BITRIX_EVENT_TOKEN` | токен приложения из формы исходящего вебхука; без него приёмник отдаёт 503 |
| `BITRIX_EVENT_PATH` | путь приёмника, по умолчанию `/b24/events` |
| `BITRIX_HTTP_SSL_CERT` / `_KEY` | сертификат и ключ для https в режиме `--http` |
| `BITRIX_TELEGRAM_TOKEN` | токен бота; только здесь, агент не меняет |
| `BITRIX_TELEGRAM_CHAT_ID` | адресат по умолчанию |
| `BITRIX_TELEGRAM_ALLOWED_USERS` | разрешённые адресаты; граница безопасности |
| `BITRIX_TELEGRAM_EVENTS` | фильтр; пусто — не пересылается ничего |
| `BITRIX_TELEGRAM_ENABLED` | принудительно вкл/выкл |
| `BITRIX_TELEGRAM_PROXY` | прокси только для Telegram |

Настройки Telegram принимаются и без префикса: `TELEGRAM_CHAT_ID`,
`TELEGRAM_ALLOWED_USERS`, `TELEGRAM_TOKEN`, `TELEGRAM_PROXY`.

Ничего из перечисленного не включается само. Без настроек сервер работает
ровно как раньше и никакого состояния не заводит.

## Если не приходит

Начните с `b24_events_stats` — он отличает «ничего не произошло» от «никто не
слушает».

| Симптом | Причина |
|---|---|
| `receiver.configured: false` | не задан `BITRIX_EVENT_TOKEN` — приёмник отвергает всё |
| Приёмник отвечает 503 | то же самое |
| Приёмник отвечает 405 | вы зашли GET'ом; маршрут принимает только POST |
| Приёмник отвечает 403 | доставка без валидного токена приложения |
| Портал не достучался вовсе | сеть; проверьте `scripts/probe_listener.py` + `curl` с Bitrix-сервера |
| Токен задан, но событий нет, транспорт stdio | приёмнику нужен `--http`; в лог пишется предупреждение |
| Канал не стартует | нет `BITRIX_WEBHOOK_URL`, либо push-сервер выключен на портале |
| `b24_changes_since` возвращает одно и то же | курсор не двигается — проверьте `cursor.advanced` в ответе |
| В базе есть, в Telegram нет | фильтр; `b24_telegram_test(preview_only=true)` |
| `cannot reach api.telegram.org` | сетевая блокировка; нужен `BITRIX_TELEGRAM_PROXY` |
| Пересылка молчит, в логе про allowed list | `chat_id` не в `BITRIX_TELEGRAM_ALLOWED_USERS` |

Скрипты проверки: `probe_listener.py` (достижимость), `pull_probe.py` (канал),
`pull_channel_check.py` (канал целиком), `poller_check.py` (курсоры),
`telegram_check.py` (фильтры офлайн), `telegram_live_check.py` (реальная
отправка), `tg_conn_probe.py` (сеть до Telegram).
