# Руководство по использованию

[English](USAGE.md) · **Русский**

Как управлять инструментами Bitrix24 MCP. Документ не привязан к конкретному
клиенту — предполагается лишь, что твой агент или код умеет говорить по MCP и
вызывать инструменты сервера. Подключение сервера к конкретному клиенту — в
разделе о подключении в README.

## Два слоя

- **Универсальный хребет** — `b24_call`, `b24_batch`, `b24_test_connection`,
  `b24_list_methods`. `b24_call` вызывает *любой* REST-метод, то есть покрывает
  весь API. Бери его, когда не подходит типизированный инструмент или чтобы
  перепроверить его поведение.
- **Типизированные инструменты** — `b24_<домен>_<действие>` (напр. `b24_crm_list`,
  `b24_task_add`). Эргономичные обёртки с корректной пагинацией, фильтрами и
  учётом нюансов Битрикса.

Начинай сессию с `b24_test_connection`, чтобы подтвердить вебхук и увидеть
текущего пользователя, затем `b24_list_methods` — чтобы понять, какие scope есть
у вебхука.

## Авторизация

Каждый инструмент принимает опциональные `webhook_url` и `personal_webhook`.
Порядок резолва: `personal_webhook` > `webhook_url` > заголовок `X-B24-Webhook`
(HTTP-транспорт) > env `BITRIX_WEBHOOK_URL`. Чтобы действовать/писать от имени
конкретного пользователя, передай его `personal_webhook`. Формат всегда
`https://<портал>/rest/<user_id>/<токен>/`.

## Фильтры

Объекты фильтра повторяют Битрикс. У ключей могут быть префиксы-операторы:

| Префикс | Значение | Пример |
|---|---|---|
| (нет) | равно | `{"STAGE_ID": "NEW"}` |
| `>` `<` `>=` `<=` | сравнения | `{">=DATE_CREATE": "2026-01-01"}` |
| `!` | не равно | `{"!STATUS": "5"}` |
| `%` | подстрока | `{"%TITLE": "invoice"}` |

Коды полей различаются по методам (CRM — `UPPER_CASE`; современные `crm.item.*`
и `catalog.*` — `camelCase`). Используй инструменты `*_fields` (напр.
`b24_crm_fields`), чтобы узнать точные коды и id перечислений перед записью.

**Исключение:** `b24_department_get` — у битриксового `department.get` вообще
нет серверного фильтра (подтверждено вживую: любой `filter`, включая `ID`,
молча игнорировался, отдавалось всё дерево отделов). Инструмент фильтрует на
стороне клиента, так что `filter`/`ID` всё равно работают как задокументировано
— просто ценой одной дополнительной полной выгрузки под капотом.

## Пагинация

Списочные инструменты возвращают конверт:

```json
{ "items": [...], "count": 50, "total": 214, "start": 0,
  "next": 50, "has_more": true, "truncated": false }
```

- Листай вручную, передавая `start` = предыдущий `next`.
- Либо передай `fetch_all: true`, чтобы автоматически пройти все страницы. Это
  ограничено `BITRIX_MAX_PAGES` (по умолчанию 40 страниц ≈ 2000 записей); при
  достижении лимита конверт покажет `truncated: true` — молча выборка не
  обрывается. Всегда добавляй `filter`, чтобы держать `fetch_all` в рамках.

## Ошибки

Ошибки возвращаются как данные, никогда не скрываются:

```json
{ "error": true, "code": "ACCESS_DENIED", "method": "crm.deal.list",
  "message": "Access denied." }
```

Частые коды: `ACCESS_DENIED` (у действующего пользователя нет прав на портале —
не баг; scope у вебхука необходим, но недостаточен), `ERROR_METHOD_NOT_FOUND`
(модуль не установлен), `B24_READONLY` (запись заблокирована read-only-режимом),
`NO_WEBHOOK` (вебхук не резолвится), `TIMEOUT`.

## Режим только чтение

Установи `BITRIX_READ_ONLY=1`, чтобы отклонять каждый write-метод ещё до отправки
на портал (чтение продолжает работать). Полезно, чтобы дать доступ только на
чтение или на время отладки. Сними переменную, чтобы разрешить запись.

## Batch

`b24_batch` выполняет до 50 вызовов одним запросом, с обратными ссылками:

```json
{ "commands": [
    {"key": "deal", "method": "crm.deal.add", "params": {"fields": {"TITLE": "New"}}},
    {"key": "note", "method": "crm.timeline.comment.add",
     "params": {"fields": {"ENTITY_ID": "$result[deal]", "ENTITY_TYPE": "deal", "COMMENT": "created"}}}
  ], "halt": true }
```

`$result[key]` / `$result[key][field]` подставляют вывод более раннего вызова.

## Рецепты

- **Сделки, созданные в этом месяце:**
  `b24_crm_list` entity=`deal`, filter `{">=DATE_CREATE":"2026-07-01"}`, select `["ID","TITLE","OPPORTUNITY","STAGE_ID"]`.
- **Расшифровать код стадии сделки в имя:**
  `b24_crm_status_list` entity_id=`DEAL_STAGE` (или `DEAL_STAGE_7` для воронки 7).
- **Задачи в колонке Scrum-доски:** `b24_scrum_board` group_id=… — получить
  активный спринт + стадии, затем `b24_tasks_list` filter `{"GROUP_ID":…, "STAGE_ID":…}`
  — приблизительно, см. «Известные ограничения» ниже.
- **Перенести задачу на Scrum-доске спринта:** `b24_scrum_task_move` task_id=…
  sprint_id=… stage_id=… — **не** `b24_task_update` с `STAGE_ID` (принимается,
  корректно читается назад, но карточку не двигает — см. «Известные
  ограничения»).
- **Создать задачу и записать время:** `b24_task_add` → затем `b24_task_elapsed_add`.
- **Скачать файл с Диска:** `b24_disk_file_content` file_id=… (возвращает base64;
  ограничено `max_size_mb`).
- **Написать в чат:** `b24_im_message_add` dialog_id=`chat123` или id пользователя.
- **Пригласить людей на событие календаря:** передай `extra: {"attendees": [id, ...]}`
  в `b24_calendar_event_add` (или `fields` в `b24_calendar_event_update`) —
  `is_meeting` выставится автоматически, как только `attendees` не пуст.

## Известные ограничения

- **Scrum-доски спринтов: перенос карточки — это два вызова, и `STAGE_ID` его не
  подтверждает.** Установлено наблюдением за боевой доской, потому что все
  задействованные вызовы рапортуют об успехе независимо от результата:

  | Вызов | Что делает на самом деле |
  |---|---|
  | `tasks.task.update` + `STAGE_ID` | Меняет поле и пишет видимую всем запись в историю — **карточка не двигается**. Худший случай: коллеги читают в логе «стадия изменена», а на доске она в старой колонке. |
  | `kanban.addTask` | **Кладёт** карточку, которой на доске *нет*. Для уже разложенной возвращает `true` и не делает ничего. |
  | `kanban.deleteTask` | Снимает карточку с доски (в спринте задача остаётся). |
  | `task.stages.movetask` | Возвращает `false` — он про обычный групповой канбан, а не про спринты. |

  Поэтому перенос — это `deleteTask`, затем `addTask`; именно так и работает
  `b24_scrum_task_move`. Вопреки названию, `deleteTask` убирает только
  *раскладку по колонке* — задачу он не удаляет и дубля карточки не оставляет.
  Сравнение до и после реального переноса: тот же id, тот же GUID, та же дата
  создания, story points, чек-лист, списанное время и теги на месте, добавилась
  одна запись в историю; на доске ровно одна карточка. Повторные переносы
  безопасны. Проверять результат через `b24_task_get` **нельзя**:
  `STAGE_ID` показывал `0`, пока карточка стояла в целевой колонке.
  Задокументированного метода `tasks.api.scrum.kanban.*`, который отдаёт список
  задач в колонке, нет, поэтому `b24_tasks_list` с фильтром по `STAGE_ID` на
  доске спринта — это приблизительно. Надёжное чтение — pull-канал: событие
  `tasks / task_update` несёт `BEFORE.STAGE`, `AFTER.STAGE` и `AFTER.STAGE_INFO`
  с id колонки, см. [EVENTS.ru.md](EVENTS.ru.md).
- **Бэклог ↔ спринт — другой механизм, и он работает.**
  `tasks.api.scrum.task.update` с полем `entityId` переносит задачу между
  бэклогом группы и спринтом, и это действительно срабатывает: `entityId` в
  `tasks.api.scrum.task.get` меняется сразу. У этой сущности есть id спринта,
  story points и сортировка, но **колонки нет**: позиция карточки в колонке
  просто не входит в REST-модель.
- **Комментарии задач лежат в одном из двух мест, и Битрикс не говорит, в каком.**
  Старые порталы держат их в forum-топике (`task.commentitem.*`); порталы, где у
  задачи есть чат, держат их там, а `forumTopicId` остаётся пустым. Чтение
  только форума на таком портале возвращает `[]` для задачи, у которой
  комментарии явно есть, — успешный `b24_task_comment_add` выглядит как
  провалившийся, и естественная реакция — отправить его ещё раз.
  `b24_task_comments_list` сначала читает форум, при пустом результате падает в
  чат и сообщает `source`, поэтому пустой ответ означает «там ничего нет», а не
  «искали не в том месте». В записях из чата присутствуют и системные уведомления
  Битрикса (задача создана, списано время) с пометкой `is_system`.
- **События календаря приходят целиком, поэтому запрашивай меньше.** У
  `calendar.event.get` нет ни серверной проекции полей, ни постраничности: он
  отдаёт все поля всех событий диапазона. Месяц по одному пользователю — 232
  события × 60 полей ≈ 1 МБ. Поэтому `b24_calendar_event_list` подрезает на
  клиенте — компактный набор полей и `limit=50` по умолчанию — но всегда
  сообщает истинный `total` и флаг `truncated`. Расширяй осознанно
  (`select=['*']`, больший `limit`), а не считай, что хвост пуст.
- **Скачивание с Диска требует, чтобы IP сервера был разрешён на портале.**
  `b24_disk_file_content` резолвит `DOWNLOAD_URL` и скачивает его на стороне
  сервера, но WAF некоторых порталов отдаёт `403 Forbidden` (HTML) на этот
  запрос, если он приходит не из доверенной сети портала — даже если файл
  только что залит тем же вебхуком и метаданные (`b24_disk_file_get`)
  прекрасно читаются. Это сетевая/WAF-политика портала, а не баг клиента:
  попроси админа портала добавить хост, где крутится `bitrix-mcp`, в белый
  список, либо запускай сервер из сети, которой портал уже доверяет.

## SPA / Смарт-процессы

Для элементов Смарт-процессов передавай `entity_type_id` в CRM-инструменты — они
автоматически переключаются на современный API `crm.item.*` (напр. `b24_crm_list`
entity_type_id=1030).

## Поиск нужного метода

В API Битрикса 1930 документированных методов. Не угадывайте сигнатуру — спросите:

```
b24_method_search("call recording attach")   → telephony.externalCall.attachRecord
b24_method_schema("crm.item.list")           → параметры, типы, что обязательно
b24_scope_gaps()                             → чего не хватает этому вебхуку
```

Каталог собран из официальной документации и покрывает в том числе методы,
которых нет в выдаче `methods` самого портала (`tasks.task.list`,
`crm.item.list`, `catalog.product.list`, `sale.order.list` и другие) — именно
поэтому он не строится по ответу портала.

`b24_scope_gaps` нужен, когда вызов упал с `ERROR_METHOD_NOT_FOUND`: на живом
портале это чаще означает **невыданный скоуп**, а не отсутствие модуля.
Перевыпустите вебхук с нужными галками.

Обновить каталог: `python scripts/build_catalog.py`.

## События портала

Сервер умеет узнавать об изменениях в портале и хранить их историю. Три способа
получения — pull-канал, приёмник исходящего вебхука, поллер — выбираются по
тому, где запущен сервер и что пропускает сеть.

```
b24_events_poll()                             новые события
b24_events_ack(ids=[...])                     пометить обработанными
b24_events_history(entity="task",
                   entity_id="477818",
                   since="7d")                архив: что было с объектом
b24_changes_since(feed="tasks")               поллер
b24_events_stats()                            что настроено и что поймано
```

`b24_events_history` отвечает на то, чего REST не умеет: у большинства сущностей
Битрикса нет истории изменений, а у scrum-доски нет и способа узнать текущую
колонку задачи. Здесь это есть — из пойманных событий.

Пересылка в Telegram настраивается через `b24_telegram_status`,
`b24_telegram_configure` и `b24_telegram_test`. По умолчанию не пересылается
ничего: фильтр выбирает пользователь.

Пошаговая настройка каждого способа, все переменные окружения и таблица
диагностики — [EVENTS.ru.md](EVENTS.ru.md).
